排他制御の中には、特定の行に対応しないものがあります。たとえば「同じテナントでは精算を同時に 1 つしか実行しない」「ある外部 ID のインポートを並行して走らせない」といったケースです。Postgres の **アドバイザリーロック（advisory lock）** は、`bigint` のペア（または単一の `bigint`）をロック名として使い、テーブル構造には縛られません。

## セッションロックとトランザクションロック

```sql
-- トランザクションレベル：COMMIT/ROLLBACK で自動的に解放
SELECT pg_advisory_xact_lock(42, hashtext('tenant:7:settle'));

-- セッションレベル：明示的に unlock するか、接続を切断する
SELECT pg_try_advisory_lock(hashtext('job:import:99'));
-- ... 処理を行う ...
SELECT pg_advisory_unlock(hashtext('job:import:99'));
```

- **`pg_advisory_xact_lock`**：トランザクションに従うため、コネクションプールと相性が良いです（借りた接続を返却した後までロックを持ち続けることはなく、トランザクション終了時に解放済みです）。
- **`pg_advisory_lock`**：セッションレベルです。プール利用時は **同じ接続** で lock/unlock を行い、返却前に解放することを保証しなければなりません。そうしないと、別のリクエストが残ったロックに引っかかります。

`try_` 系はノンブロッキングで、取得できなければ即座に `false` を返します。「誰かが処理中ならスキップする」用途に向いています。

## キーの選び方

- 安定していること：同じ業務上の意味は常に同じ `bigint`（または 2 つ組の `(classid, objid)`）に対応させます。
- システム内の他のアドバイザリーロックの範囲と衝突しないようにします。`classid` を業務ごとの番号帯に固定する方法があります。
- `hashtext` / `hashtextextended` には衝突の可能性があります。重要な経路では明示的に割り当てた整数のほうが安全です。

## 行ロック・一意制約との関係

| 手段 | 用途 |
| --- | --- |
| `UNIQUE` / 排他制約 | データそのものの排他 |
| `SELECT … FOR UPDATE` | 既存の行をロックする |
| アドバイザリーロック | ロックすべき行がない、または複数テーブルにまたがる「論理的なクリティカルセクション」 |

制約で表現できるものは制約を優先します。アドバイザリーロックは「処理フロー」の排他を補うもので、データの整合性を代替するものではありません。

## 運用

```sql
SELECT * FROM pg_locks WHERE locktype = 'advisory';
```

ロックが長時間保持されている場合は、保持しているバックエンドと `query_start` を確認します。アプリケーション側では `try_` の失敗をメトリクスとして記録し、重要なジョブが黙ってスキップされないようにします。

## まとめ

- ロックすべき行がない業務上の排他にはアドバイザリーロックを使い、プール利用時はトランザクションレベルを優先します。
- セッションロックは必ず同じ接続でペアにして unlock します。
- 制約はデータの正しさを、アドバイザリーロックは処理フローを守ります。キーは安定させ、観測可能にしておきます。
