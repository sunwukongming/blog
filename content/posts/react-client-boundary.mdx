Vue 3 那套治理推完之后，我也在几个 React 项目里踩过 RSC 的边界。最常见的误区是：要么整页 `"use client"`，等于退回 CSR；要么反过来，把带事件的组件硬塞进服务端树，构建直接报错。

## 我怎么划

- **默认服务端**：读数据、拼布局、渲染静态文案、把 Markdown 变成 HTML。这些不需要浏览器 API。
- **客户端小岛**：表单、看板娘、游戏棋盘、依赖 `window` / `localStorage` 的东西。边界用 `"use client"` 标在**真正需要交互的叶子**上，而不是整棵路由树。
- **跨边界传数据**：只传可序列化的 props。函数、class 实例、带循环引用的对象，都会在边界上炸掉。

## 一个实际坑

曾经把「列表 + 筛选」整块标成 client，结果筛选状态、请求、空态全在浏览器里跑，首屏 JS 明显变大。后来改成：服务端先按 URL searchParams 算出列表，客户端只挂一个轻量的筛选条，改条件就 `router.push`。体验几乎一样，包小了一截。

## 和 Vue 的对照

Composition API 的心智是「逻辑复用」；RSC 的心智是「默认不进浏览器」。两边都能做好前端，但规范文案不能照搬：Vue 项目强调类型与脚手架，React 项目还要额外写清**客户端边界清单**，否则每人随手加 `"use client"`，治理又回到原点。

边界划清之后，观测和性能优化也更好做：服务端那段进 Trace 的是数据获取，客户端那段才是交互延迟。
