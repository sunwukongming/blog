HTTP/2 在一条 TCP 上多路复用：一个丢包，整条连接的窗口与重传会拖住所有流——**队头阻塞（HoL）** 仍在传输层。HTTP/3 把会话建在 **QUIC**（通常 UDP）上，流之间丢失互不拖死。

## 分层直觉

```text
HTTP/3  ← 语义仍是 HTTP（方法、头、伪头）
   ↑
QUIC    ← 连接、加密、流、重传（≈ TCP+TLS 合体）
   ↑
UDP
```

- 握手：常 1-RTT（甚至 0-RTT 复用），证书与密钥协商在 QUIC 里完成。  
- 连接迁移：连接 ID 不绑死四元组，Wi-Fi ↔ 蜂窝切换可不断。  
- 拥塞控制：仍有，只是实现从内核 TCP 挪到用户态 QUIC 栈。

## 和 HTTP/2 比什么

| | HTTP/2 + TCP | HTTP/3 + QUIC |
|---|---|---|
| 丢包影响 | 连接级阻塞 | 流级 |
| 握手 | TCP + TLS 分开 | 合并，更短 |
| 中间盒 | 到处都有 | UDP/443 可能被拦 |
| 调试 | tcpdump 成熟 | 要看 qlog / 专用工具 |

浏览器与 CDN 已广泛支持；你的源站是否开启，取决于入口（CDN、负载均衡、自建如 Caddy/Nginx+quic）与证书链。

## 落地核对

1. **UDP 443**（或你选的端口）在防火墙、安全组、运营商侧是否通。  
2. 证书与 HTTP/2 同源；ALPN 协商 `h3`。  
3. 观察真实比例：`Alt-Svc` / 自动升级后，有多少流量仍停在 h2（企业网、旧客户端）。  
4. 长连接与 gRPC：生态在跟进，别假设「开了 h3 所有 RPC 立刻受益」。  
5. 日志：接入 qlog 或代理侧 HTTP/3 指标，否则排障只能猜。

## 不该期待的

- 局域网低丢包场景，体感可能不明显。  
- 应用层自己串行请求，传输层再快也救不了瀑布。  
- 「上了 HTTP/3 = 不用 CDN」——边缘终止 h3、回源 h2/h1 仍是常见拓扑。

先弄清瓶颈在 **丢包/移动切换** 还是 **应用调度**；前者才是 QUIC 的主场。和站内 HTTP 缓存、客户端 Transport 文一起读，避免只换协议号。
