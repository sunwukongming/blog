很多 Go 服务早期图省事：`struct` 既当 JSON / protobuf 入参，又直接落库、又在业务里传来传去。前三个月爽，半年后改一个字段要动四层。

## 我划边界的习惯

- **DTO / Proto message**：只服务传输。校验、默认值、版本兼容都放这里。
- **领域模型**：表达业务不变量。可以没有 JSON tag，也不该为了某个前端字段长出奇怪的名字。
- **仓储模型**：贴近表结构或缓存 key。允许和领域模型不完全同构，用显式转换，而不是共用一个「巨 struct」。

转换代码看着啰嗦，但它把「接口变更」和「业务规则变更」拆开了。评审时一眼能看出：这次是契约变了，还是领域变了。

## 错误码也是边界

对外错误建议分两层：

1. **稳定的对外码**（给前端 / 调用方）：`INVALID_ARGUMENT`、`NOT_FOUND`、`CONFLICT`、`FAILED_PRECONDITION` 这类语义，尽量少而稳。
2. **对内细节**：日志和 Trace 里带上原因、实体 ID、下游错误；不要把堆栈或 SQL 原文回给客户端。

gRPC 的 `status` + 自定义 details，或 HTTP 的 problem+json，都可以，关键是**全公司约定一套**，而不是每个组发明枚举。

## 什么时候可以先不拆

内部工具、一天写完的脚本、确定不会有第二个调用方的胶水服务——硬拆三层是过度设计。但一旦出现：

- 同一模型既要给 App 又要给运营后台
- 字段开始「有时必填有时选填」
- 错误要被别的服务依赖做分支

就该立刻把 DTO 和领域拆开。债利息是复利，越晚拆越像重写。

边界清晰的服务，改起来像换零件；边界糊掉的服务，改起来像拆毛线团。
