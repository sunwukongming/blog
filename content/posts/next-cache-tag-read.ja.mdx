このサイトではすでに **revalidateTag**、**cacheLife**、**unstable_cache** を扱っています。運用でいちばんよく聞かれるのはもう半分、つまり **読み取り時に実際に何が起きているのか** です。

## 読み取り経路の 3 状態（直感）

```text
リクエスト → キャッシュキーを参照
  ├─ fresh：そのまま返す
  ├─ stale（stale ウィンドウ内）：古い値を先に返し、バックグラウンドで再検証を起動できる
  └─ miss / expire：同期的にソースから取得し、書き込む
```

`cacheLife` のプロファイルにある stale / revalidate / expire は、まさにこれらのウィンドウを表しています。`unstable_cache` の `revalidate: 秒` は「期限切れ後、次のリクエストで再充填する」に近い動きです。

## タグ無効化が読み取りにどう現れるか

```ts
// 書き込み経路 / Server Action
revalidateTag("product");

// 以降の任意の読み取り：タグ "product" 付きのエントリは後続のリクエストで無効とみなされる
const product = await getProduct(id); // unstable_cache(..., { tags: ["product"] })
```

| タイミング | 読み手に見えるもの |
|---|---|
| タグ発行直後の次のリクエスト | 通常は miss か強制再検証。古い値を延々と返し続けるべきではない |
| TTL 切れのみ、タグなし | stale ウィンドウ次第：古い値の後に新しい値になることがある |
| キーの引数が変わった | 新しいキーであり、古いエントリとは無関係 |

## トラブルシューティングのチェックリスト

1. 無効化したのに古いまま：まったく同じタグ文字列を付けているか。複数インスタンスがそれぞれ別のキャッシュを持っていないか。  
2. ときどき古い値が出る：stale ウィンドウ内で「先に返してバックグラウンドで更新」になっていないか。それはユーザーにとって許容できるか。  
3. キーの揺れ：cookie や header を関数のクロージャに取り込みながら `keyParts` や引数に含めないと、他人のエントリを読んだり、常に miss したりします。  
4. 開発時と本番ではキャッシュの挙動が異なる：`dev` だけで判断せず、本番または `next start` で検証します。

## まとめ

設定を書くときは **キーとタグ** を、障害調査のときは **この読み取りが fresh / stale / miss のどの状態か** を考えます。読み取り経路を明確にしておけば、TTL とタグが責任を押し付け合うことはなくなります。
