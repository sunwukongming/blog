缓存一挂，数据库就像没穿衣服。比「多加一层 Redis」更要紧的是：哪一类流量能打穿到存储，以及写路径上谁说了算。

## 三个词别混用

- **穿透**：查根本不存在的 key，缓存与库都没有 → 用空值短 TTL、布隆或参数校验挡住。
- **击穿**：热点 key 过期瞬间，并发全打到库 → 互斥回源、逻辑过期、或永不过期 + 异步刷新。
- **雪崩**：大面积同时过期或缓存集群故障 → TTL 加抖动、分片、多级与限流。

混在一起调 TTL，往往哪个都治不好。

## 一致性：先选模型

常见只有几档，别假装能「强一致还随便快」：

1. **Cache-aside**：业务先读缓存，未命中读库再回填；写库成功后删缓存（或短延迟双删）。简单，接受短暂旧读。
2. **写穿 / 写回**：缓存当主存，复杂度上移，适合读多写少且能接受丢失窗口的场景。
3. **订阅失效**：binlog / CDC 推失效消息，适合多服务共库，但要处理乱序与积压。

我默认 **Cache-aside + 删缓存**：失败可重试删除，比「更新缓存」更不容易留下错值。

## 击穿时我怎么做

热点 key：

- 回源加 **单飞**（进程内或 Redis SET NX），其余请求等结果或读旧值。
- **逻辑过期**：value 里带 expireAt，过期后仍返回旧数据，一个线程异步刷新。
- 真正要强时效的，用较短 TTL + 抖动，并给数据库加 **热点限流**。

## 别把 Redis 当事务外的真理

缓存不是源。对账、库存、支付状态以库（或带版本的权威服务）为准。Redis 挂了应 **降级为直打库并限流**，而不是假数据续命。

## 小结

先画故障面：不存在的 key、单个热点、大面积失效、写后读旧。再选空值、单飞、逻辑过期、删缓存或 CDC。招式可以少，边界必须清楚。
