Tailwind v4 不是「改个大版本号」。引擎、配置入口和若干工具类语义都动过。从 v3 升上来，最费时间的往往不是新特性，而是 **旧假设还在**。

## 配置从 JS 迁到 CSS

v4 更鼓励在 CSS 里用 `@import "tailwindcss"` 和 `@theme` 声明设计令牌。`tailwind.config.js` 并非完全消失，但「所有主题都在 JS 里」的习惯要改。

常见翻车：

- 构建入口仍只扫旧的 `content` 路径，新目录的类名被 purge 掉。  
- 设计 token 一半在 CSS `@theme`，一半还在旧 `theme.extend`，运行时哪份生效说不清。  
- 插件 API / 第三方插件尚未跟 v4，构建报晦涩错误。

**做法**：先定一个真相来源（建议 CSS `@theme`），JS 配置只保留暂时搬不走的 content / 插件，迁完再删。

## 类名与默认值的静默变化

部分工具类、默认色板与层级（layer）行为有调整。视觉「差不多」时，diff 里可能已经换了生成 CSS 的结构。

建议：

1. 用视觉回归（首页、文章、游戏页各一）而不是只看 build 成功。  
2. 全局搜索已废弃或重命名的类（项目自己的封装组件里最容易漏）。  
3. 自定义 `@layer` 与 v4 预flight 冲突时，明确层顺序，别靠「碰巧覆盖」。

## 与现有 CSS 并存

本站这类「大量手写 `globals.css` + 少量工具类」的项目，升级时要小心：

- 工具类和手写选择器的 **优先级** 是否因 layer 变化而反转。  
- `dark` / 多主题若靠 `html[data-world]` 一类选择器，确认 v4 的 variant 是否还按旧写法生成。  
- 不要为了「全面 Tailwind 化」在迁移 PR 里顺手重写半个设计系统——那是第二个项目。

## 构建与 DX

- 确认 PostCSS / Vite / Next 的 Tailwind 集成包版本匹配 v4。  
- CI 里加一次 **生产 build**，开发态 JIT 看不出的缺失类名会在这暴露。  
- 编辑器智能提示若仍指向 v3 数据，升级 language server / 插件，避免「提示有、构建无」。

## 迁移清单（可复制）

1. 锁依赖，读官方 Upgrade Guide，跑官方升级工具（若有）。  
2. 统一主题令牌入口，删重复定义。  
3. 修构建 content / 入口 CSS。  
4. 修废弃类名与插件。  
5. 关键路径截图或 playwright 冒烟。  
6. 再考虑用上新特性（如更细的变体），与「能编译」分开合入。

## 小结

v4 的收益是更清晰的 CSS 优先工作流；成本是旧配置心智与插件生态的空窗。把迁移当成「换引擎 + 校准令牌」，不要当成「顺便重构 UI」，成功率会高很多。
