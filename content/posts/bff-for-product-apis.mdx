全栈项目里，前端常抱怨「一个页面打七个接口」；后端又不愿为每个端定制 DTO。BFF（Backend for Frontend）卡在中间，用得好是减速带，用不好是新债。

## 我放进 BFF 的东西

- **字段裁剪与改名**：把内部 `user_id` 收成前端要的 `id`，去掉调试字段。
- **并行聚合**：首页卡片需要用户、订单摘要、库存三处数据，BFF 并发拉齐再拼，浏览器只打一枪。
- **端差异**：App 要压缩列表，Web 要完整筛选参数——用不同 BFF 路由或 query profile，而不是让核心域服务长出 `?for=ios`。

## 我坚决不放的东西

- **核心业务不变量**：库存扣减、价格计算、权限判定。这些进领域服务，BFF 只传结果。
- **长期状态机**：支付回调、工单流转。BFF 进程一多，状态就散了。
- **「顺便写一下」的新表**：BFF 一旦有了自己的库，很快变成没人敢动的灰箱。

## 和 DTO 边界的关系

之前写过 DTO / 领域模型拆分。BFF 可以看成**面向某个产品表面的 DTO 组装层**：它消费稳定的对内 API，对外给出易用的产品契约。错误码也建议透传或映射成前端已约定的那一小撮，而不是在 BFF 再发明一套。

## 什么时候可以不上 BFF

页面只打一两个接口、团队前后端同仓同发、没有多端差异——直接调领域 API 更简单。上 BFF 的信号通常是：端变多、扇出变大、或需要把鉴权与限流挡在公网边缘。

聚合要克制：每次想在 BFF 里加 `if`，先问一句——这是展示适配，还是业务规则在逃逸。
