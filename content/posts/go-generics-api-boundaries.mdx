Go 1.18 之后，团队里很快出现两种声音：一是「终于能写 `Map` / `Result` 了」，二是「别在 handler 上玩泛型」。两者都对——关键是 **边界**。

## 适合泛型的地方

- **数据结构与算法**：`Set[T]`、小型 cache、对有序切片的二分封装。  
- **与类型参数无关的样板**：`Lazy[T]`、重试包装、对 `comparable` 的去重。  
- **库内部**：调用方看不到的辅助类型，约束写清楚（`comparable` / 自定义 interface）。

这些地方泛型减少的是复制粘贴，不改变对外契约。

## 不适合泛型的地方

对外 API（HTTP JSON、gRPC、消息事件）需要的是 **稳定、可文档化、可生成客户端的形状**。

| 做法 | 问题 |
|---|---|
| `Handler[T any]` 直接绑路由 | OpenAPI / 客户端生成困难，错误信息变糊 |
| 泛型 DTO「万能信封」 | 版本演进时字段语义漂移，调用方靠猜 |
| 用泛型替代接口隔离 | 编译期耦合扩散到所有调用包 |

传输层要的是明确字段，不是「这个 T 在某某约束下成立」。

## 我画的线

1. **进程内域模型** 可以用泛型辅助类型（例如仓库上的 `Page[T]`），但 **序列化出口收成具体 struct**。  
2. 公共 SDK 若导出泛型，约束必须少而稳；宁可多两个具体函数，也不要 `any` 约束的「方便」API。  
3. 和反射 / `encoding/json` 打交道时，优先具体类型；泛型 + 反射往往两头不讨好。

```text
HTTP/gRPC  handler  → 具体 DTO
                 ↓
           映射函数（可手写可 codegen）
                 ↓
        域服务 / 泛型工具（内部）
```

映射层可以烦一点，但契约清晰。烦是一次性的；模糊的 `T` 是长期的。

## 和「DTO / 域边界」那篇的关系

站点里谈过 DTO 与域模型分离：泛型不会取消那条线，它只是让 **内部** 重复更便宜。若发现自己在为「少写一个 struct」而把路径参数、query、body 全揉进 `Req[T]`，停一下——那是在用泛型欠可读性的债。

## 小结

泛型是实现细节的压缩器，不是 API 设计的替代品。对内消除样板，对外保持具体、可版本化的 DTO；评审时问一句：「这个 type parameter 出了包边界吗？」出了，就要特别小心。
