全栈一人交付时，联调成本低；人一多，最费时间的往往不是业务，而是「后端以为是 number，前端当 string 解析」。

## 我用过的两层

1. **形状契约**：OpenAPI / Protobuf / JSON Schema。CI 里对 breaking change 失败（删字段、改类型、必填变了）。生成客户端类型，少手写一遍。
2. **消费者驱动契约（CDC）**：前端（或 BFF）写下「我至少要这些字段」的样例，提供者在流水线里回放。适合多团队、多端共用一个域服务。

BFF 那层如果在聚合，契约要落在**对外产品 API**，而不是每一个内部下游——否则改一次内部服务，BFF 测试全红，却和用户无关。

## 联调会议还留什么

契约过了，并不等于语义对。分页是从 0 还是 1、空列表是 `[]` 还是省略字段、错误码谁来翻译——这些写进简短的「脾气说明」，比再开两小时会对着 Network 面板猜更有效。

## 最小可行

没有精力上 Pact 也行：把关键响应 fixture 放进仓库，前端单测和后端 handler 测试共用。比纯靠口头「接口文档在飞书」要硬一点。

先对齐形状，再对齐脾气。联调应该讨论边界情况，而不是讨论 `userId` 到底在哪一层。
