Server Actions 让客户端可以直接「调用」标了 `'use server'` 的函数，写小表单很爽。一当成内部 RPC 总线，边界就开始糊——和 RSC 数据边界、客户端组件边界是同一类问题，只是入口换成了 POST。

## 适合什么

- 表单提交、增删改、登录登出  
- 需要 **progressive enhancement**（没 JS 也能 POST）  
- 突变后 `revalidatePath` / `revalidateTag` 刷新 RSC 树  

## 不适合什么

- 高频轮询、大流量读（用 Route Handler / 专用读 API + 缓存策略）  
- 任意客户端拼出来的「通用查询参数对象」当 Action 入参（序列化与校验成本高，攻击面大）  
- 把本该在 BFF 的鉴权、审计只放在「反正是 server 函数」里却不做 CSRF / 来源约束  

Action 跑在服务端，**不自动等于安全**。调用方可被伪造；要鉴权、要校验输入，和写 POST API 同级认真。

## 序列化边界

能穿过 Action 的是可序列化数据，不是函数、不是 Class 实例、不是随意的服务端句柄。实践上：

- 入参用 zod（或同类）在 Action 入口验一遍  
- 出参保持 plain data；别指望把 Prisma 对象直接丢回客户端  

和「Client Component 不能偷偷 import 服务端模块」一样：类型能通过，不代表运行时该传。

## 缓存与刷新

突变成功后要明确：

- 哪些 tag / path 失效  
- 哪些客户端状态（Zustand、URL）要同步  

只 `await createPost()` 不 `revalidate`，用户会以为写成功了但列表仍是旧 RSC 载荷。反过来，乱 `revalidatePath('/')` 会把整站静态优势打穿。

## 错误与体验

Action 抛错会变成可捕获的错误；要区分：

- 校验错误 → 回给表单字段  
- 鉴权失败 → 登录或 403 体验  
- 未知错误 → 通用提示 + 服务端日志  

不要把堆栈和内部 SQL 细节回给浏览器。

## 和 Route Handler 怎么选

| 需求 | 更合适 |
|---|---|
| 表单突变 + 刷新 RSC | Server Action |
| 对外 Webhook / 移动端共用 API | Route Handler |
| 流式读、自定义缓存头 | Route Handler |
| 同应用内简单写操作 | Action 通常更短 |

Server Actions 是 React/Next 里的**受约束 RPC**，不是取代一切后端的许可证。划清「突变 + 校验 + 再验证」，它会很香；划不清，就变成难观测、难复用的隐形 POST。
