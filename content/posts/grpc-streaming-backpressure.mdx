Unary RPC 的超时和重试大家聊得多；一换成 **server streaming / bidi**，问题变成：生产者按自己的节奏写，消费者跟不上时，帧堆在哪、谁该停。

超时（见站点里另一篇）管的是「整次调用多久该死」；背压管的是「还活着的时候别把内存写爆」。

## 流在慢在哪

典型路径：

1. 应用 `Send` / `Write`  
2. gRPC 层与 HTTP/2 流控窗口  
3. 内核与网卡  

HTTP/2 有流控，但**应用若在未感知窗口耗尽时持续分配业务对象**（大消息、未释放的迭代器），照样 OOM。流控保的是字节，不保你的领域对象队列。

## 该谁停

| 角色 | 该做的事 |
|---|---|
| 服务端推流 | `Send` 阻塞或返回资源不足时停产；别起无限缓冲 goroutine「先发出去」 |
| 客户端收流 | 处理慢就少 `Recv`；需要取消就 `context.Cancel`，让对端停 |
| 中间代理 | 明确是否做缓冲；缓冲要有上限和溢出策略 |

Go 里常见坑：用 `for range` 狂 `stream.Send`，只靠默认行为；在 Send 前又塞了一个无界 channel。背压在 channel 边界就断了。

## 实用模式

### 1. 请求驱动的窗口

客户端带 `page_size` / `max_outstanding`；服务端一次只准备这么多，等 ACK 或下一页请求再继续。语义比「盲推」清晰，也方便配额。

### 2. 可取消的生产循环

```text
for {
  select {
  case <-ctx.Done(): return
  default:
  }
  msg := next()
  if err := stream.Send(msg); err != nil { return err }
}
```

`Send` 失败（含取消、窗口相关错误）要结束生产，不要吞掉后继续算下一条。

### 3. 有界队列 + 丢弃/降级策略

必须解耦时：队列长度固定，满则阻塞生产者、丢最旧、或返回 `RESOURCE_EXHAUSTED`。把策略写进 API 文档，比默默堆内存诚实。

## 观测

- 飞行中消息数、队列长度、`Send` 阻塞时间  
- 因取消 / 资源耗尽结束的流占比  
- 单条消息体积分布（大消息会放大窗口问题）

没有这些，线上只看到「偶发 OOM」或「客户端超时」，对不上是背压还是真慢查询。

## 和 Unary 重试的边界

流式中间失败通常**不能**像 Unary 那样盲目幂等重试整段；要有可恢复的游标（`start_after`）或接受「从断点续」。把重试策略和背压策略分开设计。

流式接口的性能广告很好写；背压和取消路径写不清楚的流，上线后就是定时炸弹。先画清「谁在等谁」，再谈 QPS。
