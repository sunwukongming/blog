「用 Redis Streams 顶掉 Kafka」和「凡事上 Kafka」都常见。能记流水、能消费者组，不代表运维成本与失败模式一样。

## 各自擅长什么

| 维度 | Redis Streams | Kafka |
|---|---|---|
| 定位 | 内存为主的结构 + 可选持久，嵌在已有 Redis | 专用日志型总线，分区复制 |
| 吞吐与保留 | 适合中等流量、较短保留；大保留吃内存/AOF | 高吞吐、长保留、磁盘顺序写 |
| 运维 | 跟 Redis 一起走；要自己想清空、修剪、内存告警 | Broker、ZooKeeper/KRaft、磁盘、再均衡 |
| 生态 | 应用内简单；连接器、Schema 生态弱 | Connect、大量客户端与治理工具 |

## 语义别想当然

- **消费组**：Kafka 分区 ↔ 消费者并行度要算清楚；Streams 的消费组更像「一组游标」，热点与再均衡表现不同。  
- **至少一次**：两边都要你做幂等；Streams 的 PEL（Pending Entries List）卡住时，滞后数字和「看起来没消息」会同时出现。  
- **重放**：Kafka 按 offset / 时间重读是一等公民；Streams 也能，但内存与 `MAXLEN`/`MINID` 修剪策略要先写进设计，否则「还能重放」只是口号。

## 我怎么选（经验法则）

1. **已有 Redis、流量可控、保留短、团队不想养 Kafka** → Streams 够用（通知、轻事件、局内流水）。  
2. **多下游、长时间保留、审计重放、跨团队契约** → Kafka（或云上托管等价物）。  
3. **已经在用 Kafka，只是某个服务想「本地再缓一下」** → 别再叠一层「假总线」；用应用内队列或 Outbox，语义更干净。

和站内谈消费滞后、投递语义的文章连着看：选型错了，后面全是滞后告警与重复投递的补丁。

## 小结

Streams 不是小 Kafka，Kafka 也不是重 Redis。先写清保留时长、下游个数、能否接受再均衡与磁盘运维，再挑工具；用错的那方会在峰值和重放时找上门。
