「先抢锁再干活」在单机用 `mutex` 很直觉，搬到 Redis 却经常变成故障源。锁本身没错，错在把 Redis 锁当成了数据库事务或共识协议。

## 最小正确形态

```text
SET lock:order:42 <token> NX PX 30000
# 干活……
# 释放：仅当 value == token 时 DEL（Lua 或 GET+比较）
```

三点缺一不可：

1. **NX**：不覆盖别人的锁。
2. **过期时间**：持有者崩溃时锁会掉，避免死锁。
3. **唯一 token**：释放时只删自己的锁，避免 A 过期后 B 持锁、A 回来误删 B。

`SETNX` + 单独 `EXPIRE` 不是原子的；进程在中间挂了会留下永不过期的键。

## 误用清单

### 锁过期短于业务时间

业务跑了 40s，锁 10s 就过期 → 第二台拿到锁，两人同时改同一行。修法：

- 过期时间按 P99 业务耗时留余量；或
- 持有期间**续期**（watchdog），但续期失败要立刻停手，不能假装还持有。

续期库（如 Redisson）省事，也要把「续期失败」当成硬错误，而不是日志里飘一句。

### 用固定字符串当 value

`SET key 1 NX PX …` 然后谁都可以 `DEL key`。必须用随机 token（或持有者标识），释放走 compare-and-delete。

### 把锁当互斥事务

锁只保证「这段代码不同时跑」，不保证：

- 读到的数据在锁外没被改过（还是要版本号 / 条件更新）；
- Redis 主从切换后锁不丢（异步复制下，主写入的锁可能没到从，故障转移后另一客户端再抢一把）。

需要强互斥时，优先想 **DB 唯一约束、条件更新、出站盒**，而不是「多加一层 Redis 锁就安全」。

### 红锁（Redlock）幻觉

多独立 Redis 上多数派加锁，听起来像共识，实现细节和时钟假设一直有争议。多数业务用单实例 + 合理 TTL、或直接用 etcd / ZooKeeper / DB 行锁更诚实。不要因为名字带「红」就当 CAP 银弹。

### 锁粒度过大

一把 `lock:global` 串行化整个服务，吞吐和可用性一起掉。按资源键拆（订单号、用户 ID），并接受「不同键并行」的语义。

## 什么时候不该用

- 只是防用户双击提交 → 前端防抖 + 幂等键 / 唯一索引通常够。
- 跨服务的长事务 → 用工作流 / 状态机，而不是持锁跨 RPC。
- 已有强一致存储上的条件写 → 先用存储语义，再考虑锁。

## 落地检查

1. 获取：`SET key token NX PX`。
2. 释放：Lua `if GET==token then DEL`。
3. 持有超时可观测：超时仍在跑要告警并停止写。
4. 压测主从切换与持有超时，看是否出现双写。
5. 文档写清：锁保护的是哪段副作用，不是「整单业务正确」。

分布式锁是并发控制工具，不是正确性证明。用之前问一句：没有这把锁，数据库约束能不能拦住重复？能的话，锁只是优化，不是救命稻草。
