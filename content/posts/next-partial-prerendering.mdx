Partial Prerendering（PPR）想解决的事很具体：**同一页里，能静态的先送到浏览器，动态的用 Suspense 洞稍后补上**。不是新渲染模型炫技，是缓存与流式交付的组合拳。

## 心智模型

1. 构建（或重新验证）时生成 **静态壳**（布局、导航、不依赖请求的块）。  
2. 动态组件挂在 `<Suspense>` 里，请求时再算，流式写入。  
3. 用户先看到壳，再看到洞被填满——LCP / 可交互时间往往更好看。

若整页都是动态（强依赖 cookie、个性化），PPR 帮不上；若整页都静态，你也不需要它。

## 容易踩的坑

| 坑 | 后果 |
|---|---|
| Suspense 边界过大 | 「洞」太大，壳几乎没东西，体感回到全动态 |
| 动态 API 用在壳里 | 静态部分被动态传染，PPR 失效 |
| 和客户端状态假设冲突 | 壳 HTML 与 hydrate 后数据不一致，闪烁 |
| 缓存头 / `revalidate` 没对齐 | 壳是新的、洞是旧的，或反过来 |

和站内谈 RSC 数据边界的文章同一条线：先问「这份数据能不能离开请求」，再谈要不要放进壳。

## 实践顺序

1. 找出真正的动态源（鉴权、地域、A/B、购物车）。  
2. 把它们收进尽可能小的 Server Component，外包 Suspense + fallback。  
3. 壳用静态或长时间 revalidate；洞用短缓存或每次请求。  
4. 用生产 build 看预渲染结果，不要只信 dev。

## 小结

PPR 是「同一路由上的静态 + 流式动态」。边界画对了，首屏和个性化可以兼得；画错了，你只是多了一层难解释的缓存。先拆洞，再开旗。
