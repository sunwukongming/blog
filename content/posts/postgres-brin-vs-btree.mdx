B-tree 按键排序存叶子；BRIN 按 **物理页范围** 存 min/max（或更丰富的摘要）。两者都能加速范围扫，代价与前提完全不同。

## 对照表

| | B-tree | BRIN |
|---|---|---|
| 适用键 | 高选择性、点查 + 范围 | **与堆存储顺序强相关** 的列（时间、序列、分区键） |
| 索引体积 | 随行数涨 | 按页块摘要，通常小几个数量级 |
| 点查 `=` | 优秀 | 差（仍可能扫很多块） |
| 写入 | 维护树，随机 IO 敏感 | 追加友好；乱序写入会让摘要变「松」 |
| 运维 | `REINDEX` / 膨胀常见 | 需关注相关性；必要时 `brin_summarize_*` |

## 选 BRIN 的信号

1. 事实表按 `created_at` / `id` **基本顺序写入**，查询是「最近 N 天」。  
2. 表已经大到 B-tree 占磁盘与缓存不可接受。  
3. 可以接受「少读一些页」而不是「一次找准一行」。

```sql
CREATE INDEX ON events USING brin (created_at) WITH (pages_per_range = 32);
```

`pages_per_range` 越大索引越小、越「钝」；相关性差时再小也救不了。

## 必须 B-tree 的信号

- `WHERE id = $1`、高基数字典、JOIN 驱动键。  
- 列值与物理顺序 **无关**（随机 UUID、频繁更新中间行）。  
- 需要 `UNIQUE` / 某些排除约束。

## 别踩的坑

| 坑 | 后果 |
|---|---|
| 给乱序 UUID 建 BRIN | 摘要几乎覆盖全域，等价全表 |
| 用 BRIN 替代唯一约束 | 做不到 |
| 只看「BRIN 更小」就全换 | 点查与嵌套循环变慢 |

## 一句话

**顺序大表、时间窗扫** → BRIN；**点查、高选择、乱序** → B-tree。与 `postgres-brin-indexes`、`postgres-index-choices` 互补：专文讲机制，本文讲选型开关。
