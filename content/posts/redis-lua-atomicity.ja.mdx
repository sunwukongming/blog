業務でよくあるパターンとして、在庫を読む → 足りるか判定する → 減らす、という流れがあります。これを複数回の `GET`/`SET` に分けると、間に別のクライアントが割り込んで過剰販売が起きます。Redis の **Lua / Function** を使えば、この一連の処理を **シングルスレッドでアトミックに** 実行できます。

## 最小の在庫減算

```lua
-- KEYS[1]=stock key, ARGV[1]=delta
local n = tonumber(redis.call("GET", KEYS[1]) or "0")
local d = tonumber(ARGV[1])
if n < d then
  return {0, n}
end
redis.call("DECRBY", KEYS[1], d)
return {1, n - d}
```

```ts
const [ok, left] = await redis.eval(script, 1, "sku:42:stock", "1");
```

スクリプト内のコマンドは同じインスタンス上で直列に実行され、外部からは 1 回のラウンドトリップに見えます。戻り値は単なる文字列より配列のほうが分解しやすいです。

## KEYS / ARGV の約束事

- **KEYS**：実際のキーだけを入れます。クラスターがスロットを検証できるようにするためで、スロットをまたぐと即座に拒否されます。
- **ARGV**：数値、識別子、呼び出し元 ID など、キー以外の値を入れます。
- スクリプト内で文字列連結によってキー名を組み立ててから `CALL` しないでください。クラスターモードではスロットのチェックは KEYS のリストに依存します。

Redis 7 以降では **FUNCTION**（`FCALL`）が推奨されます。スクリプトが常駐してバージョン管理でき、`EVAL` で大きなソースを何度も送る必要がなくなります。

## レプリケーション、タイムアウト、副作用

- 書き込みコマンドは AOF やレプリケーションストリームに流れます。読み取り専用のスクリプトには `EVAL_RO` / `FCALL_RO` を使います。
- 長いループはシングルスレッドを塞ぎます。上限を設け、`KEYS *` は避けます。
- スクリプト内では「現在時刻以外の外部状態」に依存しないでください。壁時計が必要なら `redis.call("TIME")` を使い、レプリケーション遅延のセマンティクスを受け入れます。

## WATCH / トランザクション / ロックとの比較

| 手段 | 向いている場面 |
| --- | --- |
| Lua / Function | 単一キー、または同じスロットの複数キーに対する短いチェック＋書き込み |
| `WATCH`+`MULTI` | 楽観的な競合が少なく、ロジックをクライアント側に残したい場合 |
| Redlock など | リソースやサービスをまたぐ排他制御（コストが高いので慎重に） |

同一インスタンスの短いスクリプトに収まるならスクリプトを優先し、シャードやシステムをまたぐ場合にロックを検討します。

## まとめ

- 読み取り・判定・書き込みは Lua/Function で一度に行い、中間状態の競合をなくします。
- KEYS と ARGV を区別し、クラスターでは同じスロットのキーだけを扱います。
- スクリプトの実行時間を抑え、レプリケーションと読み取り専用の入口を正しく選びます。
- シャードをまたぐ処理をスクリプトで無理に抱え込まず、モデルや業務の境界を見直します。
