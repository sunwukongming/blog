JWT 当 Access Token 用得很爽：网关只验签、不查库。麻烦出在**失效**：用户点了登出、改了密码、或被踢下线，已经发出去的 token 在过期前仍然合法——除非你额外做了撤销。

## 先分清两层

| 层 | 典型做法 | 失效手段 |
|---|---|---|
| Access Token | 短 TTL（5–15 分钟）JWT | 等过期；或网关查黑名单 / 版本号 |
| Refresh Token | 长 TTL，落库或只存哈希 | 删库、轮换、家族作废 |

把「登出」只写成前端清 `localStorage`，服务端什么都不做，等于告诉攻击者：偷到的 refresh 还能续命到自然过期。

## 三种常见策略

### 1. 短 Access + 可撤销 Refresh

Access 足够短，泄露窗口可接受；Refresh 每次使用都**轮换**（rotation）：旧的立刻作废，新的写回。若检测到已作废的 refresh 再被使用，整条 refresh 家族全部作废——防重放比单纯「删当前条」稳。

适合大多数 BFF / 第一方 App。代价是要有会话表或 refresh 存储，以及并发刷新时的竞态（同一 refresh 被两个 tab 同时用）：要么串行化，要么允许短暂的 grace window。

### 2. Token 版本 / 会话世代

在 JWT claim 里带 `sv`（session version）或 `pwd_v`。改密、全局登出时把用户的版本 +1；网关除了验签再比对缓存里的当前版本。比逐 token 黑名单省空间，语义也清楚：「这人所有旧票作废」。

注意缓存一致性：版本更新后 CDN / 本地 LRU 要有短 TTL 或主动失效，否则会有几秒的「幽灵登录」。

### 3. 黑名单（jti）

把未过期的 `jti` 丢进 Redis，TTL = 剩余寿命。登出、风控踢人时写入。简单，但 Access 若开到几小时，黑名单会胀；且每次请求多一次远端读，要把「默认信任、异常才查」和「高敏接口必查」分开。

## 容易踩的坑

- **Access 很长还号称无状态**：一小时的 JWT 又没有版本/黑名单，等于放弃服务端控制权。
- **只黑 Access、不轮换 Refresh**：登出后 refresh 仍能换新 Access。
- **Cookie 与 Bearer 混用却只清一边**：HttpOnly Cookie 的会话和 localStorage 的 JWT 要同一套失效协议。
- **时钟与 leeway**：多机校验 `exp` 时留几秒 leeway 可以，但不要大到让「已登出」在网关侧还能过。

## 实践建议

1. Access ≤ 15 分钟；Refresh 轮换 + 家族作废。
2. 改密、管理端「踢下线」走会话版本，不要只靠等过期。
3. 高敏操作（转账、改邮箱）再验一步：step-up 或重新输入密码，不依赖「票还在」。
4. 观测：对 `refresh_reuse`、`version_mismatch`、黑名单命中打点，比事后翻日志找「谁还没登出」有用。

无状态与可撤销不是对立面——短寿命的无状态 Access，加上有状态的 Refresh / 版本，才是大多数业务站得住的组合。
