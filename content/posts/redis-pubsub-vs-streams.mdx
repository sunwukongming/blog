`PUBLISH` / `SUBSCRIBE` 是 **在线广播**：没人听就丢，也不 ACK。Streams 是 **可积压的日志 + 消费组**。很多「消息队列」需求其实只是前者。

## 语义差一张表

| | Pub/Sub | Streams |
|---|---|---|
| 离线 / 慢消费者 | 丢 | 可留在 stream / PEL |
| 至少一次 | ❌ | ✅（组 + ACK） |
| 回放历史 | ❌ | ✅（ID / `$` / `0`） |
| 扇出模型 | 同时在线的订阅者 | 组内分片或广播组 |
| 运维面 | 几乎无 | 裁剪、PEL、认领 |

## Pub/Sub 何时够用

- **状态通知**：配置热更、缓存失效、协作光标——丢一帧可再拉权威源。  
- **在线扇出**：聊天室在线成员、看板实时角标；订阅方挂了就当没看见。  
- **与 DB 配合**：Pub/Sub 只喊「变了」，真相仍在 Postgres / 对象存储。

```text
PUBLISH cache:user:42 invalidate
-- 订阅方收到后 DEL / 重载；错过就下次读穿透
```

不要用 Pub/Sub 做订单出站、积分扣减、任何「必须处理一次」的工作单。

## 该上 Streams 的信号

1. 消费者会挂、会扩缩，**不能丢积压**。  
2. 需要 **ACK / 重试 / 死信式认领**（见站内消费组文）。  
3. 要按 ID 回放或审计「谁在何时处理了哪条」。

此时再对比 Kafka：单区域、中等吞吐、已有 Redis 运维面 → Streams 常够；跨 DC、超大分区、生态连接器 → 才认真看 Kafka（见 Streams vs Kafka 文）。

## 反模式

| 反模式 | 更好做法 |
|---|---|
| 用 Pub/Sub 推订单，靠「别丢」 | Streams + 幂等消费者 |
| 用 Streams 只推「灯亮了」且从不 ACK | Pub/Sub 或 keyspace 通知 |
| Pub/Sub + 本地队列假装可靠 | 可靠路径直接 Streams/MQ |

## 一句话

**通知、可重建** → Pub/Sub；**工单、要确认** → Streams（再谈组与 PEL）。选错的代价通常是「上线很安静，故障那天才发现消息蒸发了」。
