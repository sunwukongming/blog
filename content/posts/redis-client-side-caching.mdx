summary: Redis 6+ 的 client-side caching（TRACKING / RESP3 invalidate）让热点键留在进程内，失效由服务器推送。和普通 TTL 本地缓存、旁路 Cache 的分工不同。
---

读多写少的键，若每次都打 Redis，RTT 与连接池都是税。**客户端缓存**在应用进程留一份副本，并用 Redis 的失效通知保持不太错——不是「再套一层 TTL 糊弄过去」。

## 机制概览

1. 客户端开启 `CLIENT TRACKING ON`（常配合 RESP3）。  
2. 读过的键被服务器记下「谁关心」。  
3. 键被改/删时，服务器发 **invalidate**；客户端丢掉本地副本。  
4. 下次读未命中再回源 Redis。

```text
App memory  --miss-->  Redis
     ^ invalidate         |
     +------ RESP3 -------+
```

## 和常见本地缓存

| | 本地 TTL Map | Redis client-side caching |
|---|---|---|
| 失效 | 时间到或手写 delete | 以服务器写路径为准（仍有竞态窗口） |
| 一致性 | 多实例各过各的 | 每实例独立 TRACKING，仍需接受短暂旧读 |
| 适用 | 配置、近似值 | 单键热点、会话旁路、权限快照等 |

它不是跨实例的一致性协议；**每个进程各自一份**，只是失效更及时。

## 实践边界

1. **键基数**：跟踪太多键会占服务器与客户端元数据；只对真正热点开。  
2. **广播 vs 重定向**：`BCAST` 前缀模式省登记、通知更粗；默认精确跟踪更省流量、更费登记。  
3. **集群**：槽迁移、MOVED 时要确认客户端库是否正确重订 TRACKING。  
4. **与站内 Lua/Pipeline 文**：写路径仍要原子；缓存层不解决写竞争。

## 一句话

**热点读 + 可接受极短旧值** 时开 TRACKING；配置类继续短 TTL，强一致读别靠客户端缓存。
