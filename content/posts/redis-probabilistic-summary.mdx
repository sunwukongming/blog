RedisBloom 模块里一堆「差不多对」的结构。专文已写过 Bloom 与 Cuckoo；这里只做 **决策表**：你要的语义是什么，再挑工具。

## 决策表

| 需求 | 结构 | 误差 | 删除 |
| --- | --- | --- | --- |
| 挡穿透「一定没有」 | Bloom `BF.*` | 假阳性 | 基本不行 |
| 可撤销成员 | Cuckoo `CF.*` | 假阳性；满则踢出失败 | 可以 |
| 有多少独立用户 | HyperLogLog | ~0.8% 基数 | n/a |
| 热 key / Top-N | Top-K / Count-Min | 近似计数 | 视实现 |

精确成员 → `SET`/`SISMEMBER`；概率结构换的是 **内存**，不是正确性合同。

## 组合套路

```
写路径：业务落库成功 → BF.ADD / CF.ADD
读路径：BF.EXISTS=0 → 直接空；=1 → 查缓存/DB
需要删黑名单：CF；日切重建：BF 往往更省
UV：HLL；排行热词：Top-K，勿用 HLL 充数
```

## 运维共性

- `RESERVE` 时把容量与误差说死；监控满载与踢出。
- 与业务 key 同槽/同前缀，避免交叉 slot 脚本。
- 文档里写清「假阳性时必须回源」，防止误把概率当权限。

## 小结

- 先写清语义（成员 / 可删 / 基数 / 热度），再选结构。
- Bloom 与 Cuckoo 不是升级关系，是删除能力与空间的权衡。
- HLL/Top-K 答的是别的问题，别混进 EXISTS 路径。
