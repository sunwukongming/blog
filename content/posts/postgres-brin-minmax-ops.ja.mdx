`USING brin (col)` でデフォルトで使われるのは **minmax-ops** です。`pages_per_range` ページごとのページ範囲について、「その範囲で見つかった最小値と最大値」を 1 つ記録します。ヒストグラムでもブルームフィルタでもなく、単なる区間のサマリーです。

## ページ範囲に含まれるもの

比較可能な型の場合、各サマリーにはおおよそ次の内容が含まれます。

| フィールド | 意味 |
|---|---|
| `min` / `max` | そのページ範囲にある非 NULL 値の下限／上限 |
| NULL 関連のフラグ | すべて NULL か、NULL を含むか（具体的な列名はメジャーバージョンによって多少異なります） |

`WHERE ts BETWEEN $a AND $b` のようなクエリでは、プランナーがサマリーを確認します。条件の区間と `[min,max]` が **重ならない** ならページ範囲全体をスキップでき、重なる場合はヒープページを読んでからフィルタする必要があります。つまり BRIN の強みは「読むページを減らす」ことであり、「1 回で 1 行を特定する」ことではありません。

```sql
-- デフォルトの opclass を明示的に書き、inclusion / bloom と比較しやすくする
CREATE INDEX ON events USING brin (created_at minmax_ops)
  WITH (pages_per_range = 32);

-- サマリーが「緩い」かを確認：相関が悪いと max-min が大きくなり、スキップ率が崩れる
SELECT * FROM brin_page_items(get_raw_page('events_created_at_idx', 1), 'events_created_at_idx');
```

（`brin_page_items` やページ番号はバージョンやインデックスの形態によって変わります。本番では `EXPLAIN (ANALYZE, BUFFERS)` の heap blocks を基準にしてください。）

## 運用のポイント

1. **相関**：時刻順に追記されるファクトテーブルでは minmax は狭く保たれます。順不同の `UPDATE` でデータが散らばると区間が広がり、スキップが効かなくなります。  
2. **summarize**：大量ロードの後は `SELECT brin_summarize_new_values('idx')` を実行し、未サマリーのページが長く残らないようにします。  
3. **正確なカーディナリティは期待しない**：minmax には NDV がありません。列の選び方を誤ったのをプランナーのせいにしないでください。

## ひと言で

**minmax-ops = ページ範囲に付けた閉区間のラベル** です。相関が良いときにだけ安く済みます。順不同の書き込みがあるなら、まず書き込み順序を直すかパーティショニングを行い、`pages_per_range` の調整はその後です。
