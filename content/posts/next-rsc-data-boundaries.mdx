和「客户端边界」那篇互补：那边谈 `'use client'` 该画在哪，这边谈 **数据该在哪一层结束**。

## 默认放在 Server Component

- 读文件系统、CMS、内部 API、带密钥的 SDK。
- 拼好页面需要的 props：标题、列表、MDX 正文——像本站的 `getPost` / `getAllPosts`。
- 鉴权后的「能不能看」判断：在服务端否决，而不是把完整资源丢给浏览器再藏。

能静态或按路径缓存的，优先让框架缓存；动态用户态再收窄到具体段落。

## 必须过到 Client 的

- 事件、本地状态、浏览器 API（`localStorage`、手势、WebGL）。
- 需要持续订阅的 UI（存在感、打字机），但 **初始快照仍可由 RSC 注入**。

传给 Client 的 props 应是 **可序列化的结果**，不是「再去打内网」的钥匙。密钥、cookie 原值、未脱敏行数据都不该出现在 client bundle 的边界上。

## 常见漏法

1. 在 Client 里 `fetch` 自家需登录的 BFF，却忘了 CSRF / 同源策略与缓存头。
2. 为了省事把整个 `post` 对象塞进 Client，附带内部字段。
3. 在 Server 里读了用户会话，又把同一查询结果缓存成静态页面。

## 我用的检查清单

- 这个数据离开 Node 进程后，泄露是否可接受？
- 交互是否真的需要它，还是只要派生出的展示字段？
- 失败时 Server 能否直接 `notFound` / error boundary，而不是让 Client 空白转圈？

## 和本站的关系

文章页：服务端取 MDX 与前后篇，Client 只承接目录、进度条、复制代码。游戏纪录则完全相反——只存在浏览器里，Server 从不假装知道你的最高分。

边界清楚以后，RSC 不是玄学，只是「默认不把数据送进浏览器」的纪律。
